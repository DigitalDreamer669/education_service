# Офлайн-режим: что сделано и как это работает

## TL;DR архитектуры

```
UI (Exam/Review/Search/BookmarksPage/...)
        │  (не изменены — тот же импорт serverProgress.ts / useQuestions / useTopics)
        ▼
serverProgress.ts (offline-first)      useQuestions.ts / useTopics.ts (cache-first)
        │  читает                              │  читает
        ▼                                      ▼
offlineStore.ts  ───────────────►  IndexedDB (src/lib/db.ts)  ◄─────────────  SW precache
        │  пишет через                          ▲                            (app shell: JS/CSS/HTML)
        ▼                                        │ фоновый refresh, когда online
syncQueue.ts (очередь + идемпотентные операции) ─┘
        │
        ▼
   Supabase (user_progress / bookmarks / exam_attempts)
```

Ни одна страница (`Exam.tsx`, `Review.tsx`, `Search.tsx`, `BookmarksPage.tsx`, `TopicDetail.tsx`) не была изменена — они как вызывали `loadReviewProgress`, `saveReviewResult`, `toggleBookmark`, `useQuestions(subject)` и т.д., так и вызывают. Изменилась только реализация этих функций.

## Что кэшируется и когда

- **Вопросы и конспекты** — маленький датасет (343 + 80 строк на все 3 предмета), поэтому кэшируются **все сразу**, в фоне, сразу после логина (`src/lib/prefetch.ts`), а не только те, что пользователь открыл. Плюс продолжают кэшироваться при каждом обычном открытии страницы (`useQuestions`/`useTopics`) — двойная подстраховка.
- **Прогресс повторения, закладки, история экзаменов** — тоже подтягиваются полностью при логине и обновляются в фоне при каждом заходе на страницу, которая их использует.
- **App shell** (весь JS/CSS/HTML билда, включая ленивые чанки страниц и mermaid-диаграммы) — прекэшируется Service Worker'ом (`vite-plugin-pwa`, Workbox `generateSW`), это единственное, что решает саму задачу "открыть сайт без сети" (данные в IndexedDB бесполезны, если не загрузился сам JS-бандл).
- **Картинки** — в приложении сейчас **нет ни одного места, которое рендерит `image_name`** из таблицы `questions` (я проверил — компонент вопроса это поле не использует). Добавил на будущее рантайм-кэш `CacheFirst` для любых image-запросов в Workbox — если/когда картинки подключат в UI, они начнут кэшироваться без дополнительных правок.

## Синхронизация: гарантии и как они достигаются без миграций

| Требование | Как сделано |
|---|---|
| Нет потери данных | Запись сначала уходит в IndexedDB (`syncQueue`), UI получает "успех" сразу; запись из очереди не удаляется, пока Supabase не подтвердит её (`sendOne` → `'ok'`). Если вкладка закрылась/сеть пропала посреди отправки — при следующем запуске очередь просто продолжает с этой записи. |
| Нет дублей | `review_result` — upsert по `onConflict: user_id,subject,question_id` (естественно идемпотентен). `bookmark_set` — вместо "toggle" в очередь кладётся **желаемое конечное состояние** (`bookmarked: true/false`); insert делается через `upsert(..., { ignoreDuplicates: true })`, delete — `delete().eq(...)`. Оба безопасны при повторе. `exam_attempt` — перед `insert` проверяется, нет ли уже строки с тем же `(user_id, subject, started_at)`, где `started_at` генерируется один раз на клиенте в момент постановки в очередь (это и есть natural idempotency key вместо client_id-колонки, которую нельзя добавить без миграции). |
| Очередь изменений | `IndexedDB.syncQueue`, FIFO, с компакцией: если пользователь офлайн 5 раз подряд поменял ответ на один и тот же вопрос — в очереди останется одна запись с последним значением, а не пять. |
| Повторная отправка / докат после обрыва | `flushQueue()` обрабатывает по одной записи; при сетевой ошибке — откатывает запись обратно в `pending` и **останавливается**, чтобы не нарушить порядок; продолжает при следующем триггере. |
| Автосинхронизация | Триггеры: событие `online`, `visibilitychange` → `visible`, таймер каждые 30 сек, попытка сразу после `enqueue()` если уже online, Background Sync API как progressive enhancement для Chrome/Android (см. ниже про iOS). |
| "Atomic sync" | **Честная кросс-табличная транзакция здесь принципиально невозможна без серверной функции** (Edge Function/RPC), а вы просили не трогать бэкенд и не деплоить ничего через MCP (доступ read-only). Поэтому atomicity гарантирована **на уровне одной операции**: она либо подтверждена сервером целиком, либо остаётся в очереди целиком — частично применённых операций не бывает. Если позже это станет критично, естественное решение — Supabase Edge Function `sync-batch`, принимающая массив операций и применяющая их в одной SQL-транзакции; я такую функцию не разворачивал, т.к. это уже "серверная логика", а не чисто клиентское изменение, и требует вашего решения отдельно. |

## Авторизация в PWA — что выяснено и что сделано

- **Supabase Auth по умолчанию** (`createClient(url, anonKey)` без явного `storage`) уже использует `persistSession: true` с адаптером `localStorage` — сессия (access + refresh token) переживает перезагрузку страницы уже сейчас, без моих правок.
- **Refresh token сохраняется** в `localStorage` вместе с access token; SDK сам обновляет access token в фоне, когда есть сеть. Офлайн `supabase.auth.getSession()` не бьёт в сеть — читает то, что лежит в `localStorage`, поэтому вход "остаётся в силе" даже без интернета (я специально заменил использование `auth.getUser()` — которое всегда стучится в сеть — на `auth.getSession()` в `serverProgress.ts`, иначе офлайн-чтение прогресса ломалось бы просто из-за способа проверки пользователя).
- **iOS Safari, установленный PWA (Add to Home Screen)**: у standalone-режима WebKit — **отдельный** storage-контейнер от обычной вкладки Safari. Значит: если залогиниться в Safari-вкладке, а потом установить PWA — сессии там не будет, нужно будет войти ещё раз **внутри уже установленного приложения**. Это ровно то поведение, которое вы описали в требовании 1 ("установил PWA → один раз вошёл"), так что менять тут ничего не нужно — так и должно быть.
- **Перезапуск приложения (iOS/Chrome)**: для *установленных* PWA (не обычных вкладок браузера) современный WebKit не применяет 7-дневную ITP-очистку скриптозаписываемого хранилища — таким образом, `localStorage` с сессией не подчищается автоматически. Обычная вкладка Safari (не установленный PWA) под это правило всё ещё подпадает, но это не ваш сценарий по ТЗ.
- **Офлайн при холодном старте** (сеть отсутствует уже в момент открытия приложения): работает, потому что (1) сам SW отдаёт закэшированный `index.html`+JS/CSS без сети, (2) `AuthContext` вызывает `getSession()`, который не требует сети, (3) вопросы/конспекты/прогресс уже лежат в IndexedDB с прошлого раза.

## Что НЕ сделано / сознательно не тронуто

1. **PNG-иконки** сгенерированы простым рендером существующего `favicon.svg` через `sharp` — это devDependency, не попадает в клиентский бандл.
2. **RLS на `public.bookmarks` отключён** — это существующая проблема безопасности проекта, не связанная с офлайном; сообщил отдельно, SQL для фикса привёл, но не применял (доступ к Supabase у меня строго read-only, да и решение — ваше).
3. **AI-поиск (`aiSearch.ts`)** остался полностью онлайн-only, как и был — это отдельная, явно опциональная фича ("Спросить ИИ" по кнопке), обращение к OpenRouter без сети технически невозможно и не требовалось по ТЗ (офлайн должен работать локальный поиск по вопросам/конспектам — он и так был client-side и просто выигрывает от того, что данные теперь лежат в IndexedDB, а не только in-memory).
4. **Схема БД не менялась**, миграций не создавалось, деплоя edge functions не производилось — всё сделано поверх существующих таблиц и существующих RLS-политик клиентским кодом.

## Как проверить локально

```bash
npm install
npm run build
npm run preview      # или любой статический сервер над dist/
```

Открыть `http://localhost:4173`, зайти под своим аккаунтом (один раз — это и прогреет офлайн-кэш), затем в DevTools → Network → Offline и убедиться, что работают экзамен/повторение/поиск/конспекты/закладки/навигация. Ответы в офлайне появятся в бейдже внизу экрана ("N изменений ждут синхронизации") и уйдут сами, как только вернуть сеть.
